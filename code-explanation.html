1 What is a .env file?
A .env file (short for "environment") stores secret values that your app needs to run — like passwords, API keys, and database addresses. Instead of writing these values directly inside your code (which is dangerous), you put them here and read them with process.env.VARIABLE_NAME.

PORT=5000 — Your server will listen on port 5000. Think of a port like a door number on your computer.
MONGO_URI — The address of your MongoDB database. localhost = your own computer, 27017 = MongoDB's default port, codealpha_ecommerce = database name.
SESSION_SECRET — A secret password used to encrypt user sessions (login tokens). If someone knows this, they could fake logins.
NODE_ENV — Tells the app if it's running for development (testing) or production (real users).
🔑 Analogy: The .env file is like your house's key safe — it holds important access codes in one secure place, separate from the house itself.
⚠️
NEVER share this file The .gitignore file is set up to exclude .env from Git — that's why it's listed there. If you push this to GitHub, anyone could access your database.

ecommerce/backend/server.js
Server Entry Point — The App's Starting Engine
This is the FIRST file Node.js runs. It starts everything — the web server, database connection, and all routes.
backend/server.js
// Line 1: Load the .env file first — before anything else
require('dotenv').config();

// Lines 2-6: Import all the tools we need
const express = require('express');       // web framework
const session = require('express-session'); // login sessions
const cors    = require('cors');            // allow browser requests
const path    = require('path');            // work with file paths
const connectDB = require('./config/db');   // our database connector

// Line 8: Create the Express app — like starting the engine
const app = express();

// Line 11: Connect to MongoDB immediately
connectDB();

// Lines 14-26: MIDDLEWARE — code that runs on EVERY request
app.use(cors({ origin: true, credentials: true }));
app.use(express.json());              // parse JSON from requests
app.use(express.urlencoded({ extended: true }));
app.use(session({
  secret:           process.env.SESSION_SECRET,
  resave:           false,
  saveUninitialized:false,
  cookie: {
    secure:  process.env.NODE_ENV === 'production',
    httpOnly:true,
    maxAge:  7 * 24 * 60 * 60 * 1000  // 7 days in milliseconds
  }
}));

// Line 29: Serve the HTML/CSS/JS frontend files
app.use(express.static(path.join(__dirname, '../frontend')));

// Lines 32-34: Connect routes — each file handles its own URL paths
app.use('/api/auth',     require('./routes/auth'));
app.use('/api/products', require('./routes/products'));
app.use('/api/orders',   require('./routes/orders'));

// Line 42: Catch-all — for any URL not matched above, serve index.html
app.get('*', (req, res) => {
  res.sendFile(path.join(__dirname, '../frontend/index.html'));
});

// Lines 46-50: Start listening on port 5000
const PORT = process.env.PORT || 5000;
app.listen(PORT, () => {
  console.log(`Server running on http://localhost:${PORT}`);
});
1 What is require()?
require() is Node.js's way of importing a library or file — like import in Python. When you write require('express'), Node looks in your node_modules folder (which npm created) and loads the Express library.

When you write require('./config/db'), the ./ means "look in this same project folder" and load that specific file.
🔧 Analogy: Like using import pandas as pd in Python — you bring in a tool before you use it.
2 What is Middleware? (app.use())
Middleware is code that runs automatically on every request that comes into the server, before it reaches your route handlers.

Think of it like a security checkpoint at an airport — every passenger (request) goes through the same checks before reaching the gate (route).

express.json() — Reads the JSON body from requests (like login data) and makes it available as req.body
cors() — Lets the browser talk to the server (browsers block cross-origin requests by default)
session() — Sets up cookie-based login sessions so the server remembers who is logged in
3 Sessions & Cookies
maxAge: 7 * 24 * 60 * 60 * 1000 — This calculates 7 days in milliseconds. Let's break it down:
7 days × 24 hours × 60 minutes × 60 seconds × 1000 milliseconds = 604,800,000 ms

httpOnly: true — The session cookie cannot be accessed by JavaScript in the browser. This protects against XSS attacks (hackers stealing your cookie via JavaScript).
secure: true in production — In production, cookies are only sent over HTTPS (encrypted connections), not plain HTTP.

ecommerce/backend/config/db.js
Database Connector — Bridges Node.js to MongoDB
One job: connect to MongoDB when the server starts. If it fails, shut down the server.
backend/config/db.js
const mongoose = require('mongoose');  // Mongoose = tool to talk to MongoDB

// Define the function that connects to the database
const connectDB = async () => {
  try {
    // Connect using the URL from .env file
    const conn = await mongoose.connect(process.env.MONGO_URI);

    // If successful, print which server we connected to
    console.log(`MongoDB Connected: ${conn.connection.host}`);

  } catch (error) {
    // If connection failed, print error and STOP the app
    console.error(`MongoDB Error: ${error.message}`);
    process.exit(1);  // Exit with error code 1
  }
};

// Export this function so server.js can use it
module.exports = connectDB;
1 async/await — How JavaScript handles waiting
Connecting to a database takes time — the computer has to send a message over the network and wait for a reply. async/await is JavaScript's way of waiting for slow operations without freezing everything else.

async before a function means "this function might have to wait for something".
await before a line means "pause here until this finishes, then continue".

Without async/await, your code would try to use the database before the connection was ready, causing crashes.
☕ Analogy: Like ordering coffee and waiting at the counter (await) instead of going back to your seat and having to keep checking if it's ready.
2 try/catch — Safe error handling
try { ... } catch (error) { ... } is a safety net. Code inside try runs normally. If anything goes wrong (an error is thrown), the code inside catch runs instead of crashing the whole app.

process.exit(1) — If the database can't connect, there's no point keeping the server running. This shuts it down with error code 1 (0 = success, 1 = error — a common convention in programming).
3 module.exports — How Node.js shares code between files
In Node.js, every file is its own isolated module. To make a function available to other files, you must export it with module.exports.
Then in server.js, const connectDB = require('./config/db') imports it.
This is how all the files in this project communicate with each other.

ecommerce/backend/middleware/auth.js
Auth Middleware — The Security Guard
Two functions that protect routes — one checks if user is logged in, one checks if they are an admin.
backend/middleware/auth.js
// GUARD 1: Is anyone logged in at all?
const requireAuth = (req, res, next) => {

  // req.session.userId is set when a user logs in
  if (!req.session.userId) {
    // No userId in session = not logged in. Send 401 Unauthorized.
    return res.status(401).json({ success: false, message: 'Please login to continue' });
  }
  // User IS logged in — pass control to the next function (the route handler)
  next();
};

// GUARD 2: Is the user an ADMIN?
const requireAdmin = (req, res, next) => {

  // Check BOTH: must be logged in AND have role = 'admin'
  if (!req.session.userId || req.session.role !== 'admin') {
    // 403 = Forbidden (you're logged in but don't have permission)
    return res.status(403).json({ success: false, message: 'Admin access required' });
  }
  next();
};

// Export BOTH functions as an object
module.exports = { requireAuth, requireAdmin };
1 The three magic parameters: req, res, next
Every Express middleware and route handler receives these three objects:

req (request) — Everything about the incoming request. Who sent it, what data they sent, what cookies/session they have. req.session.userId is the user's ID stored in their session cookie.

res (response) — Used to send something BACK to the browser. res.json() sends JSON data. res.status(401) sets the HTTP status code.

next — A function that says "I'm done here, move to the next step". If you don't call next(), the request just hangs and never gets a response.
🏃 Analogy: Imagine a relay race. req is the baton, res is the finish line. next() passes the baton to the next runner.
2 HTTP Status Codes
Status codes tell the browser whether the request succeeded or why it failed:

200 — OK (success)
201 — Created (a new resource was made)
400 — Bad Request (you sent wrong/missing data)
401 — Unauthorized (you need to log in)
403 — Forbidden (logged in, but don't have permission)
404 — Not Found (the resource doesn't exist)
500 — Internal Server Error (something broke on the server)

ecommerce/backend/models/User.js
User Model — The Blueprint for a User in the Database
Defines exactly what fields a User record has, their types, and special behaviour (like hashing passwords automatically).
backend/models/User.js
const mongoose = require('mongoose');
const bcrypt   = require('bcryptjs');  // password hashing library

// Define the SCHEMA — the shape/structure of a user record
const userSchema = new mongoose.Schema({

  name: {
    type:     String,
    required: [true, 'Name is required'],  // [rule, error message]
    trim:     true   // removes spaces from start/end automatically
  },

  email: {
    type:      String,
    required:  [true, 'Email is required'],
    unique:    true,      // no two users can have the same email
    lowercase: true,      // always store emails in lowercase
    trim:      true
  },

  password: {
    type:      String,
    required:  [true, 'Password is required'],
    minlength: 6           // minimum 6 characters
  },

  role: {
    type:    String,
    enum:    ['user', 'admin'],  // only these two values allowed
    default: 'user'              // new accounts are 'user' by default
  },

  address: {   // a nested object (like a dictionary inside a dictionary)
    street: String,
    city:   String,
    state:  String,
    zip:    String,
    country:String
  }

}, { timestamps: true });  // auto-adds createdAt and updatedAt fields


// PRE-SAVE HOOK — runs automatically BEFORE saving to DB
userSchema.pre('save', async function(next) {

  // Only hash if password was changed (skip if updating email, etc.)
  if (!this.isModified('password')) return next();

  // Hash the password with cost factor 10 (how many times to scramble it)
  this.password = await bcrypt.hash(this.password, 10);
  next();  // continue with saving
});


// CUSTOM METHOD — compare a plain password with the stored hash
userSchema.methods.comparePassword = async function(candidatePassword) {
  return bcrypt.compare(candidatePassword, this.password);
  // returns true if they match, false if not
};

// Create and export the Model (a class that represents the 'users' collection)
module.exports = mongoose.model('User', userSchema);
1 What is a Schema and Model?
A Schema is like a blueprint or a table definition. It says "every User document in the database MUST have these fields, with these types and rules".

A Model is a JavaScript class built from that schema. It gives you methods to Create, Read, Update, and Delete records:
User.create() — insert a new user
User.find() — find users
User.findById() — find one user by ID
User.findByIdAndUpdate() — update a user
📐 Analogy: Schema = the form template (empty fields). Model = the stamp/machine that creates and manages those filled forms.
2 How does password hashing work?
bcrypt.hash('mypassword123', 10) converts the plain text password into something like:
$2b$10$N9qo8uLOickgx2ZMRZoMyeIjZAgcfl7p92ldGxad68LJZdL17lhWy

The 10 is the salt rounds — how many times bcrypt scrambles the password. More = more secure but slower. 10 is the industry standard.

The magic of bcrypt: you can NEVER reverse the hash back to the original password. But you CAN check if a new input matches the stored hash using bcrypt.compare().

So when a user logs in: you hash their input and compare it to the stored hash. If they match, the password is correct — without ever knowing what the original was.
3 Pre-save hooks — automatic code before saving
userSchema.pre('save', function() { ... }) registers a function that runs automatically every time a User document is saved.

Notice this.isModified('password') — this refers to the user document being saved. If the user only updated their email address (password didn't change), we skip re-hashing. Otherwise we'd hash an already-hashed password!

Also notice we use function keyword here, not arrow function () =>. This is because this inside a regular function refers to the document, but inside an arrow function this would be undefined.

Product Model — Blueprint for a Product in the Database
Defines the shape of every product record — name, price, category, stock, rating, and more.
backend/models/Product.js
const mongoose = require('mongoose');

const productSchema = new mongoose.Schema({

  name:  { type: String, required: [true, 'Product name is required'], trim: true },
  description: { type: String, required: [true, 'Description is required'] },

  price: {
    type:     Number,
    required: [true, 'Price is required'],
    min:      0    // price cannot be negative
  },

  category: {
    type:     String,
    required: [true, 'Category is required'],
    // enum = only these exact values are allowed
    enum: ['Electronics', 'Clothing', 'Books', 'Home',
           'Sports', 'Beauty', 'Toys', 'Other']
  },

  stock:      { type: Number, default: 0,   min: 0 },
  image:      { type: String, default: '/images/default-product.jpg' },
  rating:     { type: Number, default: 0,   min: 0, max: 5 },
  numReviews: { type: Number, default: 0 }

}, { timestamps: true });

module.exports = mongoose.model('Product', productSchema);
1 Key concepts in this schema
enum — Restricts a field to only specific values. If someone tries to create a product with category: "Food", MongoDB will reject it automatically. This is like a CHECK constraint in SQL.

min / max — Validates number ranges. min: 0 on price means you can't store a negative price. min: 0, max: 5 on rating enforces the star scale.

default — If a value isn't provided when creating a product, use this default. So if you don't provide an image URL, it will use the default placeholder image.
📋 Analogy: Think of it like a SQL table: category VARCHAR NOT NULL CHECK(category IN ('Electronics','Clothing'...)) — same idea, different syntax.

ecommerce/backend/models/Order.js
Order Model — Blueprint for an Order (with nested items)
Most complex model — an order links to a user, contains an array of items, a shipping address, and tracks status.
backend/models/Order.js
const mongoose = require('mongoose');

// A NESTED schema for each item INSIDE an order
const orderItemSchema = new mongoose.Schema({
  product:  { type: mongoose.Schema.Types.ObjectId, ref: 'Product' },
  // ^ ObjectId reference = Foreign Key linking to the Product collection
  name:     String,   // stored directly so history is preserved
  price:    Number,   // price at time of purchase (won't change if product updates)
  quantity: { type: Number, required: true, min: 1 },
  image:    String
});

// The main Order schema
const orderSchema = new mongoose.Schema({

  // Link to the User who placed this order (like a Foreign Key)
  user: { type: mongoose.Schema.Types.ObjectId, ref: 'User', required: true },

  // Array of items — uses the nested orderItemSchema above
  items: [orderItemSchema],

  shippingAddress: {  // all required — can't order without an address
    street:  { type: String, required: true },
    city:    { type: String, required: true },
    state:   { type: String, required: true },
    zip:     { type: String, required: true },
    country: { type: String, required: true }
  },

  totalPrice:    { type: Number, required: true },

  status: {
    type:    String,
    enum:    ['pending', 'processing', 'shipped', 'delivered', 'cancelled'],
    default: 'pending'   // every new order starts as 'pending'
  },

  paymentMethod: { type: String, default: 'COD' },
  paidAt:        Date,  // only set when payment is confirmed
  deliveredAt:   Date   // only set when delivered

}, { timestamps: true });

module.exports = mongoose.model('Order', orderSchema);
1 ObjectId References — MongoDB's version of Foreign Keys
type: mongoose.Schema.Types.ObjectId, ref: 'User' — This creates a link between collections. The user field stores a User's _id value (MongoDB auto-generates an ID for every document).

When you do Order.find().populate('user', 'name email'), Mongoose automatically fetches the linked User's name and email and attaches it to the result. Without populate, you'd only get the ID.
🔗 SQL equivalent: FOREIGN KEY (user_id) REFERENCES users(id)
2 Why store name and price inside the order item?
Notice name: String, price: Number are stored directly inside the order item, even though we have a reference to the product.

This is intentional — it's called data denormalization. If a product's price changes tomorrow, your old order should still show the price you actually paid. If we only stored the product ID and looked it up later, we'd get today's price, not the original price. By copying the name and price at the time of purchase, we preserve the order history accurately.

ecommerce/backend/routes/auth.js
Auth Routes — Register, Login, Logout, Get Current User
Handles all user authentication. Every route here becomes a real URL the browser can call.
backend/routes/auth.js — Register endpoint
const express = require('express');
const router  = express.Router();     // creates a mini Express app for this group
const User    = require('../models/User');

// ─── POST /api/auth/register ───────────────────────────
router.post('/register', async (req, res) => {
  try {
    // Step 1: Extract the data sent by the browser
    const { name, email, password } = req.body;
    // req.body = { name: "Praveen", email: "p@g.com", password: "abc123" }

    // Step 2: Validate — did they send all fields?
    if (!name || !email || !password) {
      return res.status(400).json({ success: false, message: 'All fields required' });
    }

    // Step 3: Check if email already exists in DB
    const existingUser = await User.findOne({ email });
    if (existingUser) {
      return res.status(400).json({ success: false, message: 'Email already registered' });
    }

    // Step 4: Create user in DB (password is hashed automatically by the pre-save hook)
    const user = await User.create({ name, email, password });

    // Step 5: Start a session — "remember" this user is logged in
    req.session.userId = user._id;
    req.session.role   = user.role;

    // Step 6: Send back success + user info (NEVER send the password back!)
    res.status(201).json({
      success: true,
      user: { id: user._id, name: user.name, email: user.email, role: user.role }
    });
  } catch (error) {
    res.status(500).json({ success: false, message: error.message });
  }
});
backend/routes/auth.js — Login & Logout endpoints
// ─── POST /api/auth/login ──────────────────────────────
router.post('/login', async (req, res) => {
  try {
    const { email, password } = req.body;

    // Step 1: Find the user by email
    const user = await User.findOne({ email });
    if (!user) {
      // Say "Invalid email or password" — don't reveal WHICH is wrong (security!)
      return res.status(401).json({ success: false, message: 'Invalid email or password' });
    }

    // Step 2: Compare the typed password with the stored hash
    const isMatch = await user.comparePassword(password);
    if (!isMatch) {
      return res.status(401).json({ success: false, message: 'Invalid email or password' });
    }

    // Step 3: Password matches! Create session.
    req.session.userId = user._id;
    req.session.role   = user.role;

    res.json({ success: true, user: { id: user._id, name: user.name, email: user.email, role: user.role } });

  } catch (error) {
    res.status(500).json({ success: false, message: error.message });
  }
});

// ─── POST /api/auth/logout ─────────────────────────────
router.post('/logout', (req, res) => {
  req.session.destroy();  // delete the session from server memory
  res.json({ success: true, message: 'Logged out' });
});

// ─── GET /api/auth/me ─────────────────────────────────
router.get('/me', async (req, res) => {
  if (!req.session.userId) return res.json({ success: false, user: null });
  const user = await User.findById(req.session.userId).select('-password');
  // .select('-password') = return all fields EXCEPT the password
  res.json({ success: true, user });
});

module.exports = router;
1 Why say "Invalid email or password" instead of "Email not found"?
This is a security best practice. If you say "Email not found", a hacker knows that email doesn't exist and can try a different one. If you say "Password wrong", they know the email EXISTS and can brute-force the password.

By giving the same vague error for both cases, you don't reveal any useful information to an attacker.
2 Destructuring — unpacking objects cleanly
const { name, email, password } = req.body;

This is ES6 object destructuring. Instead of writing:
const name = req.body.name;
const email = req.body.email;
const password = req.body.password;

You write it in one line. Much cleaner! The same pattern works in Python: name, email = user_data

// GET /api/products?category=Electronics&search=phone&sort=price_asc&page=1
router.get('/', async (req, res) => {
  try {
    // Read query params from the URL (after the ? symbol)
    // page=1 and limit=12 are defaults if not provided
    const { category, search, sort, minPrice, maxPrice, page = 1, limit = 12 } = req.query;

    // Build the filter object dynamically
    const query = {};

    // Only add category filter if one was passed in the URL
    if (category) query.category = category;

    // $regex = MongoDB's search operator. Like SQL LIKE '%phone%'
    // $options: 'i' = case-insensitive (matches "Phone", "PHONE", "phone")
    if (search) query.name = { $regex: search, $options: 'i' };

    // Price range filter
    if (minPrice || maxPrice) {
      query.price = {};
      if (minPrice) query.price.$gte = Number(minPrice);  // $gte = greater than or equal
      if (maxPrice) query.price.$lte = Number(maxPrice);  // $lte = less than or equal
    }

    // Build sort object. 1 = ascending, -1 = descending
    const sortOption = sort === 'price_asc'  ? { price: 1  }   // cheapest first
                     : sort === 'price_desc' ? { price: -1 }   // expensive first
                     : sort === 'rating'     ? { rating: -1 }  // highest rated first
                     : { createdAt: -1 };                        // newest first (default)

    // PAGINATION: skip records from previous pages
    // Page 1: skip 0, Page 2: skip 12, Page 3: skip 24...
    const skip  = (Number(page) - 1) * Number(limit);
    const total = await Product.countDocuments(query);  // total matching records
    const products = await Product.find(query)
                                     .sort(sortOption)
                                     .skip(skip)
                                     .limit(Number(limit));

    res.json({
      success:  true,
      products,
      total,
      page:  Number(page),
      pages: Math.ceil(total / limit)  // total pages needed
    });
  } catch (error) {
    res.status(500).json({ success: false, message: error.message });
  }
});
1 MongoDB Query Operators — like SQL WHERE clauses
MongoDB uses special $ prefixed operators inside the query object. They map directly to SQL concepts:

{ name: { $regex: "phone", $options: "i" } } → SQL: WHERE name LIKE '%phone%'
{ price: { $gte: 500 } } → SQL: WHERE price >= 500
{ price: { $lte: 5000 } } → SQL: WHERE price <= 5000
{ category: "Electronics" } → SQL: WHERE category = 'Electronics'

You can combine them: { price: { $gte: 500, $lte: 5000 } } → SQL: WHERE price BETWEEN 500 AND 5000
2 Pagination — showing results in pages
Imagine you have 100 products but want to show 12 per page:

Page 1: skip=0, show records 1-12
Page 2: skip=12, show records 13-24
Page 3: skip=24, show records 25-36

Formula: skip = (page - 1) × limit

Math.ceil(total / limit) calculates total pages. If you have 25 products and show 12 per page: Math.ceil(25/12) = 3 pages. (ceil = round UP)
📚 SQL equivalent: LIMIT 12 OFFSET 24

// POST /api/orders — requires login
router.post('/', requireAuth, async (req, res) => {
  try {
    const { items, shippingAddress, paymentMethod } = req.body;
    // items = [{ productId: "abc", quantity: 2 }, ...]

    if (!items || items.length === 0) {
      return res.status(400).json({ success: false, message: 'No items in order' });
    }

    let totalPrice = 0;
    const orderItems = [];

    // Loop through every item in the cart
    for (const item of items) {

      // Fetch CURRENT product data from DB (to get real price and stock)
      const product = await Product.findById(item.productId);
      if (!product) {
        return res.status(404).json({ success: false, message: `Product not found` });
      }

      // Check if there's enough stock
      if (product.stock < item.quantity) {
        return res.status(400).json({ success: false, message: `Insufficient stock for ${product.name}` });
      }

      // Build the order item with DB data (not client data — can't trust browser!)
      orderItems.push({
        product:  product._id,
        name:     product.name,    // snapshot of name at purchase time
        price:    product.price,   // snapshot of price at purchase time
        quantity: item.quantity,
        image:    product.image
      });

      // Add to running total using the REAL price from DB
      totalPrice += product.price * item.quantity;

      // Deduct stock immediately
      product.stock -= item.quantity;
      await product.save();  // save updated stock to DB
    }

    // Create the order with the logged-in user's ID (from session)
    const order = await Order.create({
      user:            req.session.userId,  // who placed the order
      items:           orderItems,
      shippingAddress,
      totalPrice,
      paymentMethod:   paymentMethod || 'COD'
    });

    res.status(201).json({ success: true, order });

  } catch (error) {
    res.status(500).json({ success: false, message: error.message });
  }
});
1 Why do we fetch the product from DB instead of trusting the browser's price?
Never trust data from the browser for anything financial! A user could open DevTools, intercept the request, and change the price from ₹8999 to ₹1 before sending it.

By fetching the product from the database, we always use the real price from our server. The browser sends only the productId and quantity — we calculate the total ourselves.
2 for...of loop with async/await
Notice we use for (const item of items) instead of items.forEach().

This is important! await does NOT work inside .forEach() — it would just run everything in parallel without waiting. for...of properly pauses at each await before moving to the next item.

This ensures we check stock and deduct inventory for each product one at a time, in order.

async function login() {
  // Get values from the form inputs
  const email    = document.getElementById('login-email').value;
  const password = document.getElementById('login-password').value;

  try {
    // fetch() sends an HTTP request to the backend
    const res = await fetch('/api/auth/login', {
      method:  'POST',                     // HTTP method
      credentials: 'include',              // IMPORTANT: send session cookie
      headers: { 'Content-Type': 'application/json' },
      body:    JSON.stringify({ email, password })  // convert object to JSON string
    });

    // Parse the JSON response from the server
    const data = await res.json();
    // data = { success: true, user: { name: "Praveen", ... } }

    if (data.success) {
      currentUser = data.user;   // save logged-in user globally
      updateNavForAuth();         // update navbar to show user name
      closeModal();
      showToast('✓', `Welcome back, ${data.user.name}!`);
    } else {
      // Show error message below the form
      document.getElementById('login-msg').textContent = data.message;
    }
  } catch (e) {
    // Network error (server not running)
    document.getElementById('login-msg').textContent = 'Server error.';
  }
}
fetch() is the browser's built-in function for making HTTP requests — like calling an API.

credentials: 'include' — tells fetch to include cookies with the request. Without this, the session cookie won't be sent and the server won't know you're logged in!

JSON.stringify() converts a JavaScript object to a JSON string for sending. res.json() parses the JSON string back to an object after receiving.
Part 4 — Shopping Cart with localStorage
JavaScript — Cart Logic
// Load cart from localStorage when page loads (persists after refresh)
let cart = JSON.parse(localStorage.getItem('cart') || '[]');
// If 'cart' doesn't exist in localStorage yet, use empty array []

function addToCart(product, qty = 1) {
  // Check if this product is already in the cart
  const existing = cart.find(i => i.id === product.id);

  if (existing) {
    existing.qty += qty;   // increase quantity if already there
  } else {
    cart.push({ ...product, qty });  // add new item with spread operator
  }

  // Save updated cart to localStorage (as a JSON string)
  localStorage.setItem('cart', JSON.stringify(cart));

  updateCartBadge();  // update the count bubble on cart icon
  showToast('✓', `${product.name} added to cart`);
}

function updateCartBadge() {
  // Count total items (sum of all quantities)
  const count = cart.reduce((sum, item) => sum + item.qty, 0);
  document.getElementById('cart-count').textContent = count;
}
localStorage is a simple key-value store in the browser. Data survives page refreshes but is wiped when the browser clears data.

...product is the spread operator — it copies all properties of the product object. { ...product, qty } creates a new object with all product properties PLUS a qty field.

reduce() is like Python's sum() for arrays with custom logic. It loops through every item and accumulates a value. Here it adds up all qty values to get the total item count.

Part 6 — Debouncing (Smart Search)
JavaScript — Debounce Search
let searchTimeout = null;

function debounceSearch() {
  // Cancel any previous pending search
  clearTimeout(searchTimeout);

  // Wait 400ms after user STOPS typing, THEN search
  searchTimeout = setTimeout(() => loadProducts(1), 400);
}

/* In HTML: */
<input oninput="debounceSearch()" placeholder="Search..."/>
/* oninput fires EVERY time a key is pressed */
Without debouncing, typing "phone" would fire 5 API requests (one per letter). With debouncing, we wait until the user stops typing for 400ms before sending the request.

clearTimeout() cancels the previous timer. setTimeout() creates a new 400ms delay. So if you type "p", wait, then type "h", the first timer is cancelled and a new one starts. Only when you stop does the search actually happen.
⌨️ Analogy: Like a search bar in Google that waits for you to finish typing before showing suggestions.
